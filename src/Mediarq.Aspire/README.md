# Mediarq.Aspire

One call from your project's own `ServiceDefaults` `Extensions.cs` wires Mediarq's OpenTelemetry
instrumentation and handler-registration health check into the .NET Aspire dashboard.

```bash
dotnet add package Mediarq.Aspire --project MyApp.ServiceDefaults
```

## Usage

This is **additive, not a replacement** — call it from inside the `AddServiceDefaults()` method that
`dotnet new aspire-servicedefaults` already generated for you, alongside its own OpenTelemetry, service
discovery and resilience setup:

```csharp
// MyApp.ServiceDefaults/Extensions.cs
public static IHostApplicationBuilder AddServiceDefaults(this IHostApplicationBuilder builder)
{
    builder.ConfigureOpenTelemetry();     // generated by the template
    builder.AddDefaultHealthChecks();     // generated by the template
    builder.Services.AddServiceDiscovery();

    builder.AddMediarqServiceDefaults(typeof(Program).Assembly);   // <- add this

    return builder;
}
```

That single call:

- Subscribes the tracer/meter providers to Mediarq's `Mediarq` activity source and meter (same as calling
  `Mediarq.OpenTelemetry`'s `AddMediarqInstrumentation()` yourself), so Mediarq dispatch spans and metrics
  show up in the Aspire dashboard next to everything else.
- Registers `Mediarq.HealthChecks`' handler-registration check, so a command/query that doesn't resolve to
  exactly one handler surfaces as an unhealthy check in the dashboard instead of only failing at the first
  dispatch in production.

It does **not** reimplement OpenTelemetry/service-discovery/resilience wiring, health-check endpoint
mapping (`/health`, `/alive`), or anything else the Aspire template's own `ServiceDefaults` project already
gives you — only the Mediarq-specific pieces are added on top.
